### 歸因更正（偏離 1）

**我的 v0.2 §5.5 寫錯了。** 已實測驗證覆審的反駁：

```python
prev_codes = {d["code"] for d in prev_index["drugs"]} if prev_index else set()
```

columnar dict 是 truthy → 走 `prev_index["drugs"]` → **`KeyError: 'drugs'`**。
是 **fail loud，不是靜默失效**；`prev_codes` 不會變成空集合。

我把「下次 build 會失敗」誤讀成「guard 靜默消失」，**升 Blocker 的理由不成立**，降回 **High**。
§5.5 的修訂本身仍然必要（遷移缺口屬實），但理由必須改寫。

**但實測順帶找到一個該寫進規格的東西**：若實作者用 `.get('drugs', [])`「修」這個 KeyError，
`prev_codes` 就會變成空集合 —— **那才是真正的靜默失效**，且 build 照常成功。
這是「修一個 bug 時製造新洞」的形態，v0.3 §5.5 列為明確禁令。

## 六、自查補充（兩輪覆審均未提）

| # | 項目 | 嚴重度 | 說明 |
|---|---|---|---|
| **S5** | **§4.1.1 的理由經實測證明是錯的** | Medium | v0.2 寫「全量驗證必須與 `prepareIndex` traversal 合併，才不需第二次掃描」。實測（45,179 筆、9 次取 median）：純 prepare **31.2 ms**、合併驗證 **32.2 ms**、另掃一次 **32.0 ms**。合併 vs 另掃只差 **0.2 ms**，在噪音內（單次跨度 10+ ms）。<br>**結論不變但理由要換**：全量驗證總成本約 **1 ms**，相對 4,815 ms 首屏可忽略，所以抽驗**根本沒有效能上的理由**——而不是「因為可以合併所以免費」。「要不要合併」應降為實作自由。<br>這是「結論對、理由錯」的形態：理由錯的規格會在下次重構時無聲失效。與覆審 2.8 同源，但 2.8 只看出「與方案 (a) 有摩擦」，未察覺理由本身不成立 |

> 第二輪覆審抓到**我自己修訂時製造的矛盾（2.1）與歸因錯誤（偏離 1）**——
> 這正是 memory `codex_dual_review_workflow` 記的「第二輪只審修訂本身」的價值：
> 上個專案 17 項裡有 4 項是第一輪修訂自造的洞，本輪是 2 項（2.1、偏離 1 的錯誤歸因）。
