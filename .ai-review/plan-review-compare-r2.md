## 1. 修訂引入的新問題

### R1 — High／「完整狀態表」仍不是互斥、窮盡的判定契約

**問題**

§4.3 把「載入狀態」「日期覆蓋狀態」「價格狀態」放入同一張表，但沒有優先序與適用前提：

- 一筆有效 `priced` 若帶 `conflicting_price_interval`，同時符合 `priced` 與衝突。
- 「帶 flag」未限定為**該日有效紀錄**，可能把局部衝突擴張到首筆前、空窗或整條 history。
- 「末筆後」使用最後一筆的 `to`。長區間包覆短區間時，最後起日那筆已結束，不代表資料覆蓋已結束；與上位規格 §6.4 的累計最大迄日原則不一致。
- `records=[]`、但有 `invalidRecords` 的成功載入代號，沒有最早 `from`、最後 `to`，也不是「未載入」。
- 格式不合法、確認不存在不是 shard 載入失敗，卻没有相應的適用分支。
- 「尚未取得」直接對應 tooltip「資料載入失敗」，又與 §6.1 載入中骨架不同。

**為什麼之後更貴**

這些分支會同時影響 band、crosshair、價格線及基準；各輸出自行補判定後，就形成新的雙重真相。

**建議修法**

先區分代號取得狀態，再對成功取得的有效日期紀錄判定日期狀態；明定衝突優先序、flag 的作用區間，以及空紀錄集合的結果。首筆前／空窗／末筆後應依**有效區間聯集**定義，不依最後一列的位置。

11 個語意狀態不等於需要 11 種紋理；允許異常共用樣式是正確的，**狀態數量本身無新問題**。

### R2 — High／固定基準遇到衝突時沒有唯一答案

**問題**

§4.1 要求「完整 history 最早的 `priced` record」，§4.3 又禁止衝突列作基準。

例如最早兩列同日起始、價格不同，之後才有可唯一判定的價格：

- 跳過衝突列，改用後來的價格？
- 保留最早日期，但基準不可判定？
- 若所有 `priced` 都衝突，要顯示什麼？

最後一種情況既不是「從未有 `priced`」，也不是「有基準但區間內無可繪點」。

另外，只有部分期間重疊的長紀錄，究竟整列失去基準資格，還是只排除衝突日期，也未定義。

**為什麼之後更貴**

分母選擇會改變全部指數；晚修會推翻整組數值 golden、圖例與跨視圖一致性斷言。

**建議修法**

明定基準候選資格與無候選結果。若採「最早可唯一判定的有價日期」，須明說這是對使用者固定基準決策的精確化；不能靜默把後來的價格稱作「歷史首筆價格」。圖例須能表達「有有價紀錄，但基準無法判定」。

### R3 — Medium／固定分母解掉基準歧義，但沒有完全堵住原 H2 的漏線

**問題**

§4.1 仍用「區間內沒有可繪製的點」描述無線狀態，沒有正式定義區間相交資格。固定分母的實作仍可能只取 `from` 落在 preset 內的列，讓 `A020296321` 近三年錯誤無線。

另有三個交互作用尚未定案：

- 基準日在視窗外時，是否繪製基準 marker。
- Y 軸依視窗內資料、完整歷史，或是否包含已隱藏序列。
- §4.4「只有未來紀錄不畫主圖」與「預告要能看見」、M11「僅未來有價」之間的例外關係。

**為什麼之後更貴**

會在座標範圍、裁切、圖例、M10／M11 形成不同答案，完成圖表後需一起改。

**建議修法**

明定：

- 繪製資格是有效有價區間與視窗相交，包含跨左界仍有效的紀錄。
- 視窗外基準僅列於圖例，不增加視窗外圖點。
- Y 軸採固定且可驗證的取值集合，並明定隱藏是否影響它。
- 「全部只有未來列」及「與已有歷史代號混合」各自的主圖／band 行為。

**H2／H3 判定：** 固定基準已解決 H3 的基準隨 preset 改變問題，也解決 H2 的分母歧義；但 H2 原始案例的漏線仍須靠上述區間相交契約堵住。不能宣稱僅改分母就全部解決。

### R4 — High／輸出矩陣沒有涵蓋 §3.3 新增的代號終態

**問題**

§6.1 只有成功、失敗等五態，但 §3.3 已區分格式不合法、確認不存在、載入失敗。

成功取得 shard 但缺碼時：

- 算完整成功，CSV 可以略過它？
- 算部分失敗，摘要卻必須顯示錯誤的「載入失敗」？
- 全部不存在又應套哪一列？

M3 要六個輸出交代相同集合，而矩陣本來就允許成功列子集、停用 CSV；「相同集合」沒有區分選定集合與實際資料列集合。

**為什麼之後更貴**

涉及整頁狀態與所有輸出契約，不能只靠補一則提示解決。

**建議修法**

定義「完整成功」為所有選定碼均已取得有效且版本一致的對應資料。逐一指定不合法、不存在、失敗時的欄位與文案；停用匯出與選定集合完整性連動。

摘要表保留失敗代號欄，與 §5.1 **相容**：未知指標不可填 0 或沿用其他來源，欄位保留並顯示取得狀態即可。

### R5 — Medium／七步 URL 流程仍有兩處相互抵觸

**問題**

1. 第 6 步已「擠掉第 4 個」，第 7 步又定義 N 為截斷數。四碼加一個 `code`，第 7 步可能已無東西可截，N 變成 0。超量 `codes` 的處理也因此不唯一。
2. 「保留不合法／不存在碼」與「有效碼只剩一個便改開詳細頁、零個清空 URL」衝突。例如一個正常碼加一個不合法碼，轉頁就失去原本要求保留的異常項目。

切分早於 URL decode，也未交代 `%2C` 是分隔符還是 token 內容，以及 URL 讀取是否已解碼。

**為什麼之後更貴**

路由、提示、session 還原與精確 URL 測試會各自固定不同答案。

**建議修法**

合併步只產生完整有序清單，統一於最後一次截斷並計數；明定有效碼計數時點、異常項目是否占槽，以及 0／1 碼轉頁如何保留異常資訊。另定義解碼恰一次及編碼分隔符語意。

§3.2 的 disabled 是手動加入規則，URL 正規化可以是不同入口規則，**本身無矛盾**；應明列適用範圍。

### R6 — Medium／共享請求與移除時取消請求相衝突

**問題**

§2 要同片請求共享；§6 要「重試中移除該失敗代號 → 取消該請求；其餘結果不受影響」。

兩個仍選定代號共用同一片時，移除其中一個便取消整個請求，會影響另一個。

**為什麼之後更貴**

請求生命週期與比較集合生命週期若先綁錯，後續需重改重試及競態行為。

**建議修法**

規格改為移除該碼對請求結果的需求；只有沒有其他有效需求時才取消共享取得。驗收須包含同片兩碼重試中移除一碼。

### R7 — Medium／合併排序沒有「該代號區塊末尾」

**問題**

§5.2 全表依日期跨代號合併排序，卻要求 `invalidRecords` 置於「該代號區塊末尾」。日期交錯時不存在單一代號區塊。

此外，表格篩掉某碼後，其圖上 marker 仍可能可見，點擊時没有對應列可捲動。

**為什麼之後更貴**

會牽動表格順序、CSV 順序及 marker 對應驗收。

**建議修法**

指定異常日期列在合併表中的唯一排序位置，以及其內部穩定順序；指定 marker 目標被篩掉時的明確互動結果。不要讓實作者自行選擇解除篩選或無反應。

### R8 — Medium／M15 的全面守恆數學上不可滿足

**問題**

M15 要 records、表格、CSV、marker 的出現次數全部相同，並包含 `invalidRecords`，但：

- §2 禁止 `invalidRecords` 進圖。
- CSV 只含篩選後列。
- preset 與隱藏會排除部分圖上 marker。
- 原始事件不一定都有可繪座標。

只要存在一列日期異常，便要求它既不得進圖、又必須有對應 marker。

**為什麼之後更貴**

正確實作無法通過，最後容易靠削弱測試或添加誤導圖點取得綠燈。

**建議修法**

守恆分母分開定義：

- 表格：適用代號篩選後的 records＋invalidRecords。
- CSV：啟用時與當前表格資料列相同。
- marker：符合明定繪製資格的事件子集，逐筆回指來源。

要求來源身分與內容不錯配，不要求不同輸出的筆數天然相等。

### R9 — Medium／before/after 位元組證據對象不對

**問題**

實際 `golden_frontend_2026-09-11.json` 頂層為 `buildDate`、`index`、`shards`，內容是凍結輸入資料，不是前端摘要、band 或画面輸出。

只比此檔 before/after，前端全部算錯仍可完全相同。反過來，若「輸出位元組不變」包含內部模型序列化，合法重構僅改欄位順序也可能被拒絕。

第 0 步無程式碼是合理的；問題是「可獨立驗證」填 `—`，沒有契約定案完成條件。

**為什麼之後更貴**

會給重構錯誤的安全保證，或把內部表示誤鎖成產品契約。

**建議修法**

明列凍結輸入、固定 T、獨立預期結果及需要保持一致的可觀察輸出；位元組一致僅用於真正具有位元組契約的產物。第 0 步以決策表無歧義、各分支具確定預期結果作為完成條件。

## 2. 新架構是否成立

**H1：方向成立，契約尚未成立。** 加入未知價格與日期覆蓋狀態是必要修正，但狀態名稱齊全不等於封閉模型。需先完成 R1、R2 的優先序與適用集合。

**H4：方向成立，完整性需要分兩層。**

- 選定集合是否全部取得有效資料。
- 某個輸出依篩選／可見性應呈現哪些內容。

因此「匯出目前篩選結果」與「任一選定碼未成功便停用」**並不矛盾**：前者決定內容，後者決定是否允許產出。即使失敗碼被表格篩掉仍停用，是保守但一致的取捨，沒有理由要求恢復完整事件 CSV。

**H5：取消 N 序列門檻正確，不必改回。**

規格仍明確要求共用 `summaryAt`／`selectMeta`／`stateLabel`／`chartModel`，並非只要求「兩邊看起來相同」。已有三道防線：

1. 共用每代號判定規則。
2. 各自對獨立預期值驗證。
3. 再驗兩個視圖一致。

不足處是 M1 只完整描述摘要一致性；新增 band、crosshair、衝突排除及基準資格，尚未全部納入同一份每代號契約。**補上這些可觀察結果的共同預期，足以防雙重真相；強迫改成 N 組輸入不能提供額外語意保證。**

## 4. 仍然過度或仍然不足之處

**仍然過度**

- M15 要求所有輸出同筆數，超出合理守恆，且違反既有圖表限制。
- 把未指明的「輸出位元組不變」當作重構必要條件，可能鎖住內部表示；凍結輸入檔則又太弱。
- 不需要為 11 個語意狀態強求 11 種視覺樣式，也不需要恢復 N 序列重構門檻。

**仍然不足**

- 狀態的優先序、日期覆蓋聯集、衝突基準資格。
- URL 異常項目的保留與路由終態。
- 共享請求取消、marker 與篩選交互作用。
- M1 的共同契約範圍及 M16 的終態／轉移覆蓋。

上述必要修正均在既定目標內，與純靜態、無 build step、手刻 SVG、`data/` 不經 SW、保留 `rawPrice` 等限制相容。**本輪不建議撤回固定基準功能，也不建議改回完整事件 CSV。**
