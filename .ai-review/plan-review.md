**結論：架構方向與既定取捨相容，未見需要全面重來的 Blocker；但有數項 High 級資料契約缺口，應先定案再建立資料模型。**主要集中於 window 的適用範圍、異常區間的呈現、摘要的時間基準，以及發布資料的一致性。

## 1. 需求與邊界缺漏

**1.1｜嚴重度：High｜兩筆 window 不足以保證跨日正確**

- **問題：**A6 刻意只保留「現行、預告1」，但來源可能有預告2。當日期越過預告2，window 已無法回答現行價。另有「build 日無有效區間就清空 window」的規則，會一起遺失未來首次支付或空窗後恢復支付的資訊。spec §8.6「不會發生已過生效日仍顯示舊價」因此過度保證。
- **為什麼現在不修之後會更貴：**搜尋卡、detail、預告標籤都依賴此契約；上線後才補會牽動 index 模型及多處日期判定。
- **建議修法：**保留兩筆 window 的架構限制，但明定它是有限範圍的摘要。區分「已確認無有效紀錄」與「window 不足以判定」；後者不得顯示確定的現行價或無紀錄結論，可使用既有完整 history 判定。無現行但有未來列時，另明定未來紀錄的可見性。若要求搜尋頁完全不載入 history 就跨任意多次預告正確，則與兩筆限制衝突，必須由使用者選擇改變契約。

**1.2｜嚴重度：High｜衝突／重疊只有偵測，沒有產品語意**

- **問題：**同一天可能同時有效「10 元、20 元」或「有價、終止」。規格只要求保留、標記；未定義現行價、metadata、事件及總變化怎麼呈現。排序穩定不代表排序後第一筆就是可信答案。
- **為什麼現在不修之後會更貴：**如果先讓所有下游都假設單一有效區間，之後加入不確定狀態將改動資料模型與整套摘要。
- **建議修法：**明定受影響日期顯示「來源紀錄衝突，無法判定單一支付價」，保留候選紀錄及標記；不得把排序結果當成價格優先權。另區分同價重疊與異價衝突，限定哪些事件／統計仍可成立。這與「只標示、不修補」相容。

**1.3｜嚴重度：High｜容許少量壞日期，卻沒有可保存它們的契約**

- **問題：**bad date ≤1% 可通過，但 A2 又要求所有非重複來源列守恆。無效起日、無效迄日、起日晚於迄日如何保存、排序、計算 coverage，均未定義。尤其壞迄日不能與「開放迄日 null」混為一談。
- **為什麼現在不修之後會更貴：**先建立只接受合法 interval 的模型，後續只能在刪列、假造日期或重做模型間選擇。
- **建議修法：**定義無法形成 interval 的原始紀錄及日期錯誤標記之表示方式；保留原值，但不參與無法成立的時間推導。同步改寫守恆式，分清有效 intervals、保留的異常紀錄與去重列；bad date ratio 明定分母及同列多錯誤的計數方式。

**1.4｜嚴重度：High｜摘要的「最後」可能指向未來**

- **問題：**spec §5.1 的 `lastPricedPrice` 是「最後一個 priced」，§5.5 總變化亦取最後 priced，未排除預告。例如歷史 10 元、目前終止、未來恢復 20 元，可能顯示「終止前 20 元」。`unchanged`、`initial`、`first_priced`、`unknown` 成為最新已生效列時，最新事件卡也沒有完整規則。
- **為什麼現在不修之後會更貴：**單一 `lastPricedPrice` 未必能服務所有終止／暫停事件；補救會改摘要欄位與顯示契約。
- **建議修法：**逐項指定時間基準：終止前價格相對於該次終止事件；總變化截至已聲明的統計日期；預告不混入已生效統計。保留「跨日後統計可暫少一次」的取捨，但標明統計基準日。另定義最新事件是否跳過 unchanged，以及沒有可報告調整事件時的文案。

**1.5｜嚴重度：High｜事件判定存在重疊規則，零元語意尚未封口**

- **問題：**`[missing, priced]` 同時符合 first_priced 與 unknown；`[malformed, terminated]` 同時符合 terminated 與 unknown。首列也可能同时符合 initial 與 unknown。另「首列 0 元不可能是終止」並不能單憑資料首列證明；資料可能沒有收錄更早事件。
- **為什麼現在不修之後會更貴：**事件一旦寫入所有 history shards，調整優先順序或 state 語意將造成全量資料與 golden 重建。
- **建議修法：**補齊互斥的事件決策表與優先順序，區分「本列支付狀態已知」及「與前列的轉換無法判定」。首列零元由藥師明確決定是否只調整文案或調整 state；不要由覆審預設推翻既定零元慣例。`N/A`、`NA`、`無` 等擴充 marker 也應確認是否具有與 `-` 相同的判斷依據，並持續標明推論性質。

**1.6｜嚴重度：Medium｜前端失敗與重入路徑不完整**

- **問題：**目前只定義 shard 404、status 載入失敗。index／meta 失敗、HTTP 200 但 JSON 損毀、shard 缺少預期代號，以及使用者先選 A 再選 B 而 A 最後回應，都沒有明確結果。
- **為什麼現在不修之後會更貴：**各畫面可能自行解讀失敗，造成錯把載入錯誤當查無資料，或 B 標題下顯示 A 的價格。
- **建議修法：**定義各資源的載入中、不可用、內容不合法與成功狀態；搜尋資料尚未可用時不能宣稱查無代號。所有顯示資料須屬於目前選定代號，重試成功後須恢復正常內容。

**1.7｜嚴重度：Medium｜日期邊界與預告／空窗文案尚未一致**

- **問題：**未明文統一起迄日是否含當日、瀏覽器日期採哪個時區、頁面跨午夜是否自行更新。歷史表將所有 `to=null` 顯示為「持續有效」，也可能把未來列說成已有效。
- **為什麼現在不修之後會更貴：**ETL、搜尋與圖表可能各用不同邊界，產生一日價差且難以重現。
- **建議修法：**明訂日期區間邊界、日期基準與頁面跨日行為；可沿用瀏覽器本地日期，不要求可信時間服務。空窗、預告未生效、無迄日是不同資訊，文案應分開表達。空白搜尋及「fuzzy contains」究竟是否僅指子字串包含，也一併定義。

**1.8｜嚴重度：Low｜規格與規劃的衝突沒有覆蓋規則**

- **問題：**spec 寫 golden 10 個，plan 為 11 個；deep link 在 spec §18 延後，卻出現在 MVP 驗收；spec §13 仍有「無變化即跳過 commit」；列數與代號數門檻分別出現 `&gt;` 與「小於才 fail」。plan 又宣稱細節以 spec 為準。
- **為什麼現在不修之後會更貴：**開發與驗收可各援引不同文件，造成不必要返工或錯判驗收。
- **建議修法：**統一版本，明列 plan 覆蓋的條款，消除 100,000／5,000 等號邊界歧義；heartbeat 的 status commit 明確排除於「無變化不 commit」之外。

## 2. 架構風險

**2.1｜嚴重度：High｜缺少跨檔案、跨發布的同批資料契約**

- **問題：**index、meta、status 與延遲取得的 shard 是分開載入。即使單次部署完整，已開啟的舊頁面仍可能拿到新版 shard；新版 status 亦可能讓舊資料看起來剛確認過。A8 只保證單次產物內一致。
- **為什麼現在不修之後會更貴：**發布識別與相容性沒有進入資料契約，之後補上會牽動所有資源及載入流程。
- **建議修法：**規定每次展示的 index／shard／meta 必須屬於同一相容資料版本；status 必須能辨識它成功檢查的是哪批資料。不一致時不可組合成可信摘要。可用靜態發布版本或內容識別達成，不需要後端或資料庫。

**2.2｜嚴重度：Medium｜workflow 重疊及 commit→deploy 的成功定義缺漏**

- **問題：**排程與手動觸發重疊時，舊執行可能較晚完成；未定義何者可發布、失敗推送是否可改成成功 heartbeat。規劃也尚未具體選定 Pages 的發布路徑，不能把「commit 成功」直接當成「網站已更新」。
- **為什麼現在不修之後會更貴：**若先形成多條發布路徑，後續需重整 workflow 與狀態語意。
- **建議修法：**定義發布不得被較舊候選結果倒退覆蓋；候選資料須相對實際發布基準重新確認有效性。明確界定檢查、commit、部署各自成功的條件；驗收包含網站實際可讀到該次 status，而非只驗 repo。維持每週 status commit 的既定決策。

**2.3｜嚴重度：High｜index 契約缺少已要求展示的資料**

- **問題：**搜尋結果須显示暫停原始標記，但 window 範例只有 state、price，沒有 rawPrice。spec 要求 TFDA／給付規定連結，卻未明確配置在 index 或 history；資料品質旗標在條文中出現，所屬層級及前端可取得方式不完整。無 build 日有效列時，描述欄位來源也未定義。
- **為什麼現在不修之後會更貴：**UI 開發才發現資料不可得，就會臨時擴充檔案或增加不必要載入。
- **建議修法：**建立「畫面資訊→來源欄位→輸出位置→缺值行為」對照，尤其涵蓋 raw marker、連結、資料品質標記與描述欄位缺值。無有效描述列時可顯示代號與缺值，不預設以預告列回填，避免違反 D9。

**2.4｜嚴重度：Medium｜只比較 index／history，可能漏掉有意義的 metadata 異動**

- **問題：**來源只增加完全重複列時，去重後資料可完全相同，但 `sourceRowCount`、`duplicateRowsRemoved` 應改變。現行規則只更新 status，會留下舊計數。`generatedAt` 標為「資料最後異動日」，也可能只是 window 隨 build 日期跨界而改變。
- **為什麼現在不修之後會更貴：**歷次統計、guard 基準及 UI 更新日期會混用不同語意。
- **建議修法：**明定 meta 是「已發布資料批次統計」或「最近成功檢查統計」。若採前者，最近檢查的來源統計另有明確歸屬；若採後者，允許小型 meta 在有意義欄位改變時更新。`generatedAt` 應描述產物生成時間，不宣稱官方內容異動時間。大型資料仍只在差異時 commit。

**2.5｜嚴重度：Medium｜效能指標未測到已知的主要成本**

- **問題：**分片決策合理，但首頁 index raw 約 22 MB，比最大 history shard 更大。「index load 後 &lt;200 ms」未定義是否包含解析；gzip guard 也不能代表解析時間。spec §16 建議省略 rawPrice，與「永遠保存原值」可能衝突。
- **為什麼現在不修之後會更貴：**到 UI 完成才確認首頁不可互動，可能需要重新切分 index 與調整載入契約。
- **建議修法：**先明定既有效能目標的量測起訖、裝置及資料規模，包含 JSON 解析至可搜尋的成本。任何精簡不得失去原字串，如 `12.50` 不能以數值 `12.5` 冒充原值；相容的精簡應優先處理非必要重複資訊。

**2.6｜嚴重度：Medium｜[新增需求] 大規模語意異常的自動發布攔截**

- **問題：**現有列數與 schema guards 無法阻擋「列數正常，但大量支付價變空白／abc」或「大量原有代號被其他代號替換」；目前只有記錄計數。
- **為什麼現在不修之後會更貴：**若出現這類上游故障，網站會更新為大量異常結果，且 status 仍顯示最近成功檢查，需緊急回復。
- **建議修法：**由使用者決定是否新增「相對前次已發布資料，特定異常大幅增加時暫停發布」政策，並指定可接受門檻與處理方式。這是超出現行明列 guards 的新增政策，不預設納入；不做的具體後果即為上述故障仍可通過發布。

## 3. 驗證策略缺口

以下弱化版本均指合理可能發生的漏做或錯做，不以「專門硬編碼測試答案」作為反例。

**3.1｜A1｜嚴重度：Medium**

- **問題／弱化版本：**只正確處理五個例子；空白起日也當開放、非閏年 2/29 通過、8 碼西元被錯轉，仍可過關。
- **延後成本：**日期污染會擴散至排序、window、圖表及歷史輸出。
- **建議修法／補強斷言：**空白起日必報錯；起日不得套用迄日哨兵；有效與無效閏日各一例；8 碼西元正確；非法迄日不得變開放區間；起日晚於迄日必被標記；合法起迄日原有邊界保持不變。

**3.2｜A2｜嚴重度：Medium**

- **問題／弱化版本：**刪掉一筆終止列、重複另一筆有價列，總數仍守恆；或 classified state 正確但 priced 金額錯誤。其餘四種 suspended marker 未測。
- **延後成本：**守恆測試會對錯誤歷史提供假信心。
- **建議修法／補強斷言：**每個代號的保留紀錄須與來源去重後逐筆對應，起迄日、原價格字串、數值及狀態全部相符；所有指定 marker 均覆蓋。`12.50` 的數值須為 12.5、原字串仍為 `12.50`；非有限數值不得成為可顯示支付價。

**3.3｜A3｜嚴重度：High**

- **問題／弱化版本：**所有差額都填 null，仍通過目前大部分斷言；增加價格、四捨五入、unknown 優先權及預告排除也沒測。
- **延後成本：**事件語意若先固化進 shards，之後需重建模型期待值。
- **建議修法／補強斷言：**原序列 10→8 必為 −2、−20%；8→9 恢復必為 +1、+12.50%；第二次恢復 previousPrice=9、差額=0、crossesStop=true，仍不計調價次數。另加入漲價、四捨五入臨界值、相同狀態續期、missing／malformed 前後轉換，依定案後的互斥事件表驗證；未生效漲跌不得計入當日次數。

**3.4｜A4｜嚴重度：Medium**

- **問題／弱化版本：**只對第一組重複列正確；保留不同藥商列後，卻把同價同區間兩列算成兩次調整。三筆衝突也可能被錯算成任意筆數。
- **延後成本：**去重、衝突統計與事件之間會出現不同紀錄單位。
- **建議修法／補強斷言：**三筆全同保留一筆、移除二筆；任一非價格欄位不同均不得去重；三種價格同區間的衝突計數依明定單位精確符合；保留的同價紀錄不得憑空新增調價事件。明定「全同」採來源原字串或正規化後字串。

**3.5｜A5｜嚴重度：Medium**

- **問題／弱化版本：**僅比較相鄰列，遇到長區間包住短區間時誤報 gap；或把相差一天但實際連續的區間當空窗。
- **延後成本：**錯誤 gap 會傳到表格、圖表與摘要。
- **建議修法／補強斷言：**前段迄日次日開始不得報 gap；僅缺一天必報；端點同日依閉區間規則判 overlap；長區間包覆多筆短區間不得產生假 gap；開放區間後再出現有效列須辨識 overlap；旗標所屬紀錄、空窗日期及代號計數均須精確。

**3.6｜A6｜嚴重度：High**

- **問題／弱化版本：**只在「恰有一筆現行」時正確；無現行、多筆現行及日期跨第二次預告都失效。只測 ingredient，也容許品名或藥商取錯列。
- **延後成本：**window 的覆蓋能力與 metadata 選列契約須事後重做。
- **建議修法／補強斷言：**同一完整 history 下，所有描述欄位皆取合規的 build 日有效列；預告1是最早尚未生效列；無現行、有未來列、window 耗盡及現行衝突各有指定結果；資訊不足不得冒充「無有效紀錄」。

**3.7｜A7｜嚴重度：Medium**

- **問題／弱化版本：**把 status 時間寫死可满足 byte-identical，卻破壞 heartbeat；依輸入列次序產生不穩定結果也未必被不同 hash seed 揭露。
- **延後成本：**測試會迫使開發者弱化正確時間行為。
- **建議修法／補強斷言：**明確固定來源、build 日期及檢查時間時，全產物一致；只變更檢查時間時，僅允許指定的時間／狀態欄位異動；同一列集合任意重排後，資料內容仍一致；跨 build 日 history 不變。

**3.8｜A8｜嚴重度：Medium**

- **問題／弱化版本：**index 與 shards 同時漏掉同一代號、補入另一假代號，數量仍一致；每個代號也可能被分配到錯誤歷史。
- **延後成本：**會將全量一致誤認為來源正確。
- **建議修法／補強斷言：**來源去重後代號集合、index 集合、所有 shard 聯集完全相等；shard 間無重複；各代號紀錄屬於該來源代號；所有清單檔案存在；混合長短前綴時仍選最長符合者；前綴切分變更不得遺失歷史。

**3.9｜B1｜嚴重度：Medium**

- **問題／弱化版本：**只把 500 視為失敗，卻把 timeout、TLS 錯誤、HTTP 200 錯誤頁或截斷 CSV 當成功。
- **延後成本：**真實來源故障往往不符合單一 mock。
- **建議修法／補強斷言：**上述失敗類別均不得發布候選資料、更新成功 status 或建立資料 commit；4xx 不重試，暫時性錯誤依既定次數與間隔處理。對 HTTP 200 無效內容須經內容驗證判定，不能只看狀態碼。

**3.10｜B2｜嚴重度：Medium**

- **問題／弱化版本：**只要求支付價與起日；藥品代號缺失、必要欄位重名或列欄位錯位仍繼續。
- **延後成本：**錯誤 schema 對應可污染整份資料。
- **建議修法／補強斷言：**先列出必要欄位及可缺欄位；任一必要欄缺失、辨識歧義或結構錯位均依明定規則失敗，data／status／發布版本不變；合法欄位換序應仍產生相同資料。

**3.11｜B3｜嚴重度：Medium**

- **問題／弱化版本：**所有輸入一律 fail 就能過三項；或把 bad date 分母算成欄位數，讓其他資料量下的 1.01% 通過。代號數門檻未驗。
- **延後成本：**guard 可能在真實邊界失效或阻擋正常更新。
- **建議修法／補強斷言：**依統一後的門檻，分別測門檻下、等於及上；以獨立指定的前次已發布列數驗證 99% 邊界；同列雙日期錯誤依明定方式計數；其他條件正常的合法候選須成功；失敗不得更新 status、commit 或部署。

**3.12｜B4｜嚴重度：Medium**

- **問題／弱化版本：**永遠忽略 metadata API、填 null 並印 warning，即可過關；也可能 build 成功但未發布新的正常 CSV 資料。
- **延後成本：**官方更新時間功能形同不存在而無人察覺。
- **建議修法／補強斷言：**500、timeout、非 JSON、缺欄位均不阻擋正常 CSV 更新，發布後 sourceModifiedAt=null、UI 顯示無法取得；成功回應則精確保存合法 modifiedDate，不能仍填 null。

**3.13｜B5｜嚴重度：Medium**

- **問題／弱化版本：**每次只更新 status、從不更新價格，也能過無變化案例；只改任意 status 字元而未真正刷新 lastCheckedAt 也可能通過。
- **延後成本：**差異發布功能未被驗證，正常更新可能永遠不上線。
- **建議修法／補強斷言：**無差異時只有 status 改變，時間對應第二次成功檢查且 result=unchanged；單一價格變更時對應產物必更新，無關 shard 不變；同 CSV 跨生效日時，index／統計按契約更新、history 不變；metadata-only 異動按 2.4 的定案契約驗收。

**3.14｜B6｜嚴重度：Medium**

- **問題／弱化版本：**一律 fail，或用 raw 大小冒充 gzip 大小，都能通過單一超標案例。
- **延後成本：**可能錯擋正常資料，或漏擋高壓縮率以外的實際超標。
- **建議修法／補強斷言：**獨立確認 gzip 估計大小；低於、等於、略高於 warning／fail 門檻各有精確結果；warning 仍可發布、fail 不改既有資料與 status；任何一片超標都須觸發，不只第一片。

**3.15｜C1｜嚴重度：High**

- **問題／弱化版本：**只支援 priced→terminated；恢復支付、預告調價、暫停、空窗及 window 耗盡都錯。終止前價格若有未來恢復價也可能錯。
- **延後成本：**會把不完整的現行價模型當成已驗證。
- **建議修法／補強斷言：**覆蓋上述轉換，在生效日前、當日、後各驗搜尋與 detail；加入「10 元→終止→未來 20 元」驗終止前仍為 10；同頁跨日依既定行為切換；window 資訊不足不得顯示確定舊價。

**3.16｜C2｜嚴重度：Medium**

- **問題／弱化版本：**dataset 有 null，但畫面仍跨 null 連線；gap 沒資料點卻被兩端直線連起來。整張圖空白也符合多數現有否定斷言。
- **延後成本：**資料測試全過，最主要的視覺誤導仍上線。
- **建議修法／補強斷言：**實際圖形在所有有效 priced 區間顯示正確水平價格，僅於生效邊界階梯變動；終止、暫停、missing／malformed 與空窗不得有價格線穿越；終止／暫停區塊與預告標示可見；所有可繪製歷史與預告均在合理軸域內，不得靠裁切或空圖過關。

**3.17｜C3｜嚴重度：Medium**

- **問題／弱化版本：**22 天黃、46 天紅，但 45 天也錯誤標紅；JSON 200 但日期無效時無警示；紅色橫幅出現但現行價旁沒有加註。
- **延後成本：**使用者可能把無法驗證的新鮮度視為正常。
- **建議修法／補強斷言：**21、22、45、46 天依統一日數算法精確符合；缺欄位、無法解析時間與資源失敗均不得顯示正常新鮮；紅色時摘要現行价旁同步加註。未來時間依明定裝置日期取捨處理，不要求外部校時。

**3.18｜C4｜嚴重度：Medium**

- **問題／弱化版本：**只搜尋前 50 筆原始資料；已知測試代號剛好位於其中。英文大小寫、substring 及終止品項可被錯誤排除。
- **延後成本：**搜尋漏資料不易被使用者辨識為系統缺陷。
- **建議修法／補強斷言：**匹配項放在第 50 筆之後仍可找到；精確代號於超過 50 筆候選中仍排名第一；中文／英文／成分依定案匹配規則驗首段、中段及非匹配值；終止品項不被預設排除；空白搜尋有固定結果。若 ATC prefix 屬 MVP，須測；否則移除其 MVP 承諾。

**3.19｜C5｜嚴重度：Medium**

- **問題／弱化版本：**任何有效 code 都開同一個 detail；index 尚未載入就先判查無；根路徑可用但專案子路徑重新整理失敗。
- **延後成本：**分享網址看似可開，實際顯示錯品項或無法使用。
- **建議修法／補強斷言：**至少兩個不同 shard 的有效代號，其標題、價格、歷史均與 URL 相符；直接開啟及重新整理均成功；等待索引期間不顯示查無；不存在代號不得遺留先前品項內容。

**3.20｜C6｜嚴重度：Low**

- **問題／弱化版本：****無明顯弱化版本**，前提是「可見」確實指使用者可見全文，而非只檢查文字存在。
- **延後成本：**若誤把隱藏文字算作可見，會留下小型 UI 修正。
- **建議修法／斷言：**搜尋與 detail 在既定桌面／行動版視窗中，免責聲明全文可讀、未被截斷或遮蔽。毋須新增更長免責條款。

**3.21｜C7｜嚴重度：Medium**

- **問題／弱化版本：**顯示重試按鈕但沒有恢復行為；或錯誤時保留前一藥品圖表。
- **延後成本：**錯誤 UI 存在，仍可能造成跨品項誤讀。
- **建議修法／補強斷言：**第一次 404、第二次成功時，重試後呈現目前代號完整歷史並解除錯誤；錯誤期間不顯示其他代號內容或 0 筆結論；損毀 JSON／預期代號缺失亦走明確錯誤路徑；A 慢、B 快時不得由 A 回應覆蓋 B。

**3.22｜D1｜嚴重度：Medium**

- **問題／弱化版本：**只核對 ETL 已輸出的列；ETL 漏掉的列不會出現在核對表，仍能全部 ✓。網站數值 `12.5` 也未必能驗證 CSV 原字串 `12.50`。
- **延後成本：**golden 一旦被信任，遺漏可能長期固定為正確答案。
- **建議修法／補強斷言：**網站可取得的完整紀錄集合須與對照表雙向一致，包含列數、漏列與多列；逐列區分網站可驗證的日期／數值、CSV 原字串及藥師判定狀態。網站未提供的資訊標為不可核對，不得填 ✓；無法完成全歷史核對時，Phase 1 的完成判準須明確處理，不假設網站必然提供全部歷史。

**3.23｜D2｜嚴重度：Medium**

- **問題／弱化版本：**11 個代號都存在且原始 intervals 正確，但事件、摘要、metadata 或圖表全錯，D1／D2 仍可通過。
- **延後成本：**「具有反例代號」被誤當成「反例性質已驗證」。
- **建議修法／補強斷言：**每個代號指定防守性質：恢復不計調價、首次有價不標恢復、暫停保留原標记、空窗圖形中斷、預告不入現行、metadata 不取損毀預告列。將每個性質連至實際驗收斷言，不能只在 fixture 註解用途；11 個必選代號與「≥6」的關係亦須明確。

**3.24｜D3｜嚴重度：Medium**

- **問題／弱化版本：**在期限前填核對日期，但測試使用執行當日，10/1 後即失去預告案例。固定 golden 若拿來對比每週最新 CSV，正常新增公告或官方修正也會使 build 永久失敗。
- **延後成本：**更新流程上線後可能反覆卡住，最終誘使維護者關閉 golden。
- **建議修法／補強斷言：**獨立核對通過的固定資料，在指定參考日期下可持續重現預告及生效後結果，不因日曆推進而失效；每週最新來源與固定回歸資料分清責任。正常新增區間與既有已核對區間被改寫須有不同、明定的結果；不得由 ETL 自動覆寫預期值讓測試轉綠。

**3.25｜嚴重度：Medium｜驗收矩陣仍有未掛號的既有目標**

- **問題：**A–D 沒有直接驗收總變化、最新事件完整語意、損毀欄位的使用者可見標記、來源連結正確歸屬、history table 完整性、1／2 節所述跨版本與重疊發布，以及 spec 的效能目標。
- **為什麼現在不修之後會更貴：**即使 A–D 全過，也不能據此宣稱 MVP 全部完成。
- **建議修法：**增加既有需求對應斷言：首尾金額與參考日期可核算；全無有價／僅單筆有價有固定結果；所有保留紀錄可在表格找到；品質標記對應正確品項；連結名稱與來源吻合；發布不可倒退或混批；效能依明定量測條件達標。這些是既有承諾的驗證，不是新增產品功能。

## 4. 更簡單的替代方案

**4.1｜嚴重度：High｜減少 index 與 history 的雙重真相**

- **問題：**現行 detail 同時依 index 的 window／摘要與完整 history，會有兩套時間範圍及不一致處理。
- **為什麼現在不修之後會更貴：**每項語意修正都要同步修改兩份資料契約與測試。
- **建議修法：**搜尋頁維持兩筆 window 作摘要；detail 既已載入完整 history，可將其作為詳細時間判定的主要依據。這不新增元件、不引入後端，也保留瀏覽器日期判定。是否保留 index 的所有 detail 摘要欄位，由定案後的顯示需求決定。

**4.2｜嚴重度：Medium｜固定 golden 與最新來源檢查分工**

- **問題：**把固定人工答案同時當作轉換回歸測試、最新政府資料真值及每週發布閘門，混合了三種不同責任。
- **為什麼現在不修之後會更貴：**正常公告變動會被當成程式回歸，人工核對負擔逐次增加。
- **建議修法：**固定、獨立核對的資料負責驗證轉換與時間語意；最新來源負責結構、完整性與已定 guards。若要持續比對 golden 代號的最新來源，明定差異處理政策，避免一律要求永久 byte-identical。

**4.3｜嚴重度：Low｜不必預先增加儲存與效能元件**

- **問題：**目前實測分片與 index 的 gzip 大小尚未超標，尚無證據需要新資料服務、自動重分片系統或複雜壓縮契約。
- **為什麼現在不修之後會更貴：**若提前擴建，會增加資料契約及驗收面，卻未必改善首頁解析瓶頸。
- **建議修法：**維持靜態 JSON、前綴 shard map、uv 與每週 Actions；先把現有效能量測及超標處理寫清楚。不用 backend、SQLite-wasm 或 GAS 替代；它們與已聲明限制衝突，也沒有解決本次最主要的語意問題。

**最難回頭的三個決策，依序為：**

1. **價格狀態與事件資料模型**：零元、unknown、衝突及異常日期一旦寫進完整歷史與 golden，修改成本最高。
2. **index window 與摘要的時間契約**：決定能回答哪些日期、何時只能回報不確定，以及終止前價格是否正確。
3. **靜態資料的發布一致性契約**：決定 index、shard、meta、status 能否安全組合；晚補會跨及資料格式、發布與前端載入。
