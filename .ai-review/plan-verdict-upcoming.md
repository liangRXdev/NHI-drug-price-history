## Blocker

| # | 項目 | 判定 | 理由 |
|---|---|---|---|
| B1 | §3.4／U6 要求「upcoming.json 產生失敗不得擋 build，其餘照常發布」＝部分發布 | **接受** | 屬實，且**推翻本專案覆核者先前的評估**（原評為「方向正確」）。既有契約是 `plan.md` B8／(a)7：任一 guard 失敗 → `data/` 與 `status.json` 皆不寫入。引入單檔可獨立失敗會產生第二種發布語意。更糟的是後果具體可觀察：upcoming 失敗但其餘發布 → 舊 `upcoming.json` 留在原地、`meta.dataVersion` 已更新 → 觸發規格自己的 §5.5「dataVersion 不一致 → 不渲染清單」，功能鎖死且無自我修復路徑。<br>**修法**：改為全有全無——預告產生或驗證失敗即 exit 1，整批不發布。U6 改寫為「注入例外 → 非 0 結束，`data/` 與 `status.json` 位元組不變」，並加一條成功發布的正對照。 |
| B2 | §7 要求 `upcoming.json` 走 SW network-first ＋ 離線 fallback | **接受** | 屬實。`sw.js:25` 為 `if (url.pathname.includes('/data/')) return;`，檔頭明寫理由：資料若從 SW 快取取得會繞過 `dataVersion` 與過期警示。§7 等於為新檔開例外，且與 §5.5 互咬：離線 fallback 拿舊 upcoming、meta 走網路拿新的 → 永久 version mismatch。<br>**修法**：刪除 §7 該條，沿用「`data/` 不經 SW」，離線落到 §5.5 的不可用＋重試狀態。 |

## High

| # | 項目 | 判定 | 理由 |
|---|---|---|---|
| H1 | §4 事件標籤表混淆 `eventType` 與 `priceState`；`initial` 未定義 | **接受** | 屬實，有實證。`A020296321` 首列 1995-03-01～1998-02-28 為 `priceState: terminated`、`rawPrice: "0.00"`，但 `eventType` 是 **`initial`** 不是 `terminated`。§4 以 eventType 為索引鍵且無 `initial` 列 → 這類列在規格裡沒有標籤可用；而 §5.3 的首列 0 元例外本來就是以「priceState ＋ 該列之前有無 priced」定義的，與 eventType 無關。同理「終止→終止續期」為 `unchanged`，§4 卻一律標成「續期（價格未變）」，把 0 元說成價格不變。<br>**修法**：§4 改為 `priceState × 此前有無 priced` 為主鍵的呈現決策表，`eventType` 僅作次要修飾；保留 record 原事件不重算。 |
| H2 | §3.3「與 index 同進退」與「來源無變 → 不動 upcoming.json」自相矛盾 | **部分接受** | 問題屬實但 Codex 的歸因與修法都錯。Codex 主張修訂上位 `plan.md` B5「消除雙重規則」——不可行也不必要：實測 `build-data.yml:58` 以 `git diff --staged --quiet -- data/drug_index.json data/history` 判定 changed，B5「同 CSV 但 build 日跨過某預告生效日 → index 更新、`history/` 不變」就是現行且正確的行為。<br>真正的錯在 §3.3 自己：「與 `drug_index.json` 同進退」與「來源無變 → 不動」在**跨生效日**那一格答案相反，而跨生效日正是 `upcoming.json` 最需要更新的時刻（剛有列離開預告集合）。<br>**正確修法**：§3.3 只保留「與 `drug_index.json` 同進退」，刪除「來源無變 → 不動 upcoming.json」與「最舊落後一個 build 週期」的宣稱。**不動 B5。** |
| H3 | §3.3／U7 沒有首次上線與規則修正的產生路徑 | **接受** | 屬實且即刻會咬到：上游 `sourceModifiedAt` 現停在 2026-08-28，功能上線當天若來源未變，照原 §3.3 `upcoming.json` 永遠不會產生，功能上線即空。<br>**修法**：明定新版本首次交付必須含一份經驗證的初始 `upcoming.json`；生成規則變更屬版本遷移，與例行週檢查分開驗收。`dataVersion` 維持只依來源內容。 |
| H4 | 為一個小型衍生清單引入獨立失敗發布＋SW 快取＋離線態，複雜度不成比例 | **接受** | 與 B1／B2 同源，合併處置：保留「完整 history 產生單一 upcoming 檔、進頁才載入、同批驗證發布、data 不經 SW」。 |

## 驗證策略（U1–U12 逐條）

Codex 對 U1–U12 每一條都給出了「能通過但功能是壞的」弱化實作，**全部接受**，原文見 `plan-review-upcoming.md` §3。最關鍵的三條：

- **U1**：預期 fixture 不得由待驗生成器產生，否則錯誤輸出會先被固定成 golden。改為雙向逐筆對應、保留重數、無多無漏。
- **U5**：「完全不寫檔」「固定輸出空檔」都是 byte-identical，determinism 測試會掩護「根本沒生成」。須加一條「改一筆來源證明輸出會變」的反向哨兵。
- **U12**：每列都重複第一筆，總數仍相等——列數不是內容正確的證據。

### 母體不足，會空泛通過的驗收條件

以 D = 2026-09-11 重算全量 history 確認（Codex 與本覆核者各自獨立算出同一組數字）：

| 驗收 | 現況 | 處置 |
|---|---|---|
| **U4** | 未生效 `terminated` 共 62 列，`everPriced = false` 者 **0 列**。整個母體沒有實例，人工目檢也驗不到。 | 必須用合成 fixture，規格明寫。另加「曾有價後終止」的正對照，防止實作把所有終止都改成 0 元文案。 |
| **U2** | 全量有 3 個代號各帶 2 筆未生效紀錄（`X000342121`、`X000346219`、`X000359219`），但**全不在凍結快照的 11 碼內**。 | 合成 fixture 或擴充快照母體；擴充時母體不可縮成剛好等於子集。 |
| **U1** | 凍結快照只產生 3 筆未生效列，事件只有 `increase`／`terminated`。 | §4 的 9 種標籤中 `initial`／`suspended`／`relisted`／`first_priced`／`unknown` 在全量未生效集合裡也是 0 筆，必須指名反例補足，不得以「掃完 82 列」代替。 |
| U6／U8／U10／U11 | 失敗、到期、混批條件都不會自然出現。 | 一律主動注入。 |
