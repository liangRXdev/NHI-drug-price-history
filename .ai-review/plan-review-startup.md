## 1. 需求與邊界缺漏

### 1.1【High】meta 失敗後，已取得的 index 沒有後續轉移契約

**問題：** D2 要求 meta 失敗即啟動 index；§6 又要求此時 index 不可用。但沒有定義：index 成功後是否保留、屬於哪個狀態，以及 meta 重試成功後如何重新驗證。`idle/loading/ready/error/mismatch` 無法直接表達「取得成功但尚未驗版本」。現有 [`validateIndex()`](engine.js:514) 在沒有 meta 時會回成功，因此這不是沿用現況就能安全處理的情境。

**晚修成本：** 會同時影響狀態模型、重試規則、資源保存與所有視圖閘門；最後才補容易出現未驗版本搜尋或永久無法恢復。

**規格修法：** 定案一條完整路徑：未驗 index 是保留等待驗證，或明確丟棄並在 meta 恢復後重新取得。列出兩種到達順序、meta 重試取得不同版本、舊 index 回應最後抵達時的結果；搜尋須同時滿足 meta ready 與 index 已對該 meta 驗證成功。

### 1.2【High】序號只保障畫面仍不足，快取與共用狀態也須有有效範圍

**問題：** §5.3 只說丟棄過期回應，沒有界定是在寫 DOM 前，還是在更新快取、比較資料與錯誤旗標前。現有 [`loadShard()`](app.js:1101) 會先寫快取；比較流程也會在最後的序號檢查前更新共用狀態。詳情與比較另有不同的 shard 取得路徑。

可觀察反例：詳情 A 尚未回應 → 切比較頁且請求同片 → 再切搜尋 → 舊比較回應版本不符；即使沒有重畫，仍可能留下錯誤旗標或污染快取。

**晚修成本：** 快取有效性、重試與導覽會互相纏繞；單補最後一道序號判斷無法解決。

**規格修法：** 明定每個回應對「視圖、快取、錯誤旗標、落定通知」各自是否仍有效。涵蓋詳情／比較同片重疊請求，以及 meta 世代改變後舊請求抵達；過期回應不得改動新世代的可觀察狀態。

### 1.3【Medium】3,000 ms 的起算、重設與同時觸發未定義

**問題：** 「自導覽開始」可能指首次開站、每次 `popstate`，或每次重試。若連續換頁就重設，可能永遠延後 index；若舊計時器未失效，重試期間又可能提早啟動。計時到期、主要資源落定及搜尋導覽同時發生，也只有「一次」宣告，沒有明確轉移規則。

**晚修成本：** 各入口會各自解讀計時器生命週期，之後須重整觸發流程。

**規格修法：** 指定時間基準與失效條件，列出 2,999／3,000／3,001 ms 落定及三種觸發交會的預期結果。HTTP 成功但內容驗證失敗也應明確算落定。

### 1.4【Medium】比較頁無請求、轉址與部分失敗的「落定」有缺口

**問題：** D2 只定義「該次比較的所有 shard 請求 settle」，未涵蓋零個有效代號、單一有效代號轉詳情、無匹配前綴、全部命中快取、比較途中增刪品項。§5.2「meta ready → 正常」也省略了比較／預告自身 loading、error、mismatch、retrying 狀態。

現有 [`showCompare()`](app.js:1229) 確實包含單品項轉址與空集合分支。

**晚修成本：** 容易留下永不啟動 index、等待已不存在的比較工作，或部分完成就提早啟動的分支。

**規格修法：** 明列無網路請求的立即落定條件、轉址後的責任歸屬，以及選定集合改變後哪次工作仍能觸發 index；矩陣補上主要資源狀態。

### 1.5【Medium】D4 的條件優先序有歧義

**問題：** D4 第一列要求空碼／非法字元直接查無，最後一列又要求 meta 未就緒時絕不查無。`?code=` 在 meta loading/error 時，兩列同時成立。S8 也漏掉空碼及不符合現行長度但合法英數的反例。

**晚修成本：** UI、測試與錯誤優先序可能分別採用不同解讀。

**規格修法：** 明定判定順序，區分「輸入語法無效」與「資料中不存在」。逐一指定空碼、空白碼、非法字元在 meta loading/error/ready 時的畫面，以及合法非 10 碼存在於 shard 時必須成功。

### 1.6【High】「沒有匹配前綴＝查無」新增了對 shard map 完整性的依賴

**問題：** 現有 [`validateMeta()`](engine.js:506) 只檢查外層型別；空 `files`、清單成員型別錯誤、清單與 versions 不一致，都不一定被拒絕。D4 卻把無匹配前綴直接當成存在性證據，會讓不合法 meta 遮蔽成查無。

**晚修成本：** 查無判定建立在不足的前提上；之後須一起修改 meta 合法性、錯誤分類與驗收資料。

**規格修法：** 定義足以支撐查無的 shard map 合法性條件；map 本身不合法只能顯示資料錯誤。這是 D4 的必要前置條件，不是擴充資料格式或另加快取需求。

## 2. 架構風險

### 2.1【High】D3 的論證只涵蓋詳情主體，沒有涵蓋同畫面的 index 品名

**問題：** 「index 不參與數字」不足以證明「同一畫面不混批」。比較籃仍顯示 index 品名，比較主體也有 index 品名 fallback。若 mismatch 時仍保留或發布 `byCode`，舊 shard 價格可能配上另一批品名。

**晚修成本：** D3 是本案最難回頭的契約變更；若各處已認定非搜尋視圖不需管 index 版本，之後要重新清查所有呈現來源。

**規格修法：** 把論證改為：畫面上每個 index 衍生內容都必須來自已對目前 meta 驗證成功的 index。`error/mismatch/未驗證` 時不得發布其品名，也不得保留其他 meta 世代的名稱。保留詳情決策不變。

### 2.2【Medium】mismatch 不代表目前頁面一定是「更新前的資料」

**問題：** GitHub Pages 也可能給新 meta＋新 shard＋舊 index。此時頁面是新資料，§5.5 卻宣稱它是更新前資料。版本雜湊只能判斷不同，無法判斷新舊。

此外，`status.json` 的新鮮度資訊與 meta 沒有版本連動驗證；D3 的「自洽」應限定為主體資料，不能擴大宣稱整頁所有來源同批。

**晚修成本：** 文案會成為測試與人工驗收的固定契約，之後修正須同步修改多處。

**規格修法：** mismatch 文案只陳述已知性質：搜尋資料與目前頁面的版本不一致，需要重新整理；不要斷言版本方向。這項文案修正有具體誤導風險，符合前提 (a)8。status 本案若維持現況，應明列其不在同批保證內，不必順勢擴充功能。

### 2.3【High】§5.6 的代號聯集相等，無法保證前端找得到代號

**問題：** 將代號從正確 shard 移到錯誤 shard，聯集仍完全相等；重複放在多片也會被集合消掉。前端依最長匹配前綴選片，仍可能得到錯誤查無。這正是 D4 將原有資料缺陷改判查無的未列出後果。

**晚修成本：** 守門通過會被當成 D4 安全性的證據；資料路由缺陷進入正式資料後才會暴露。

**規格修法：** 守門除集合相等外，還須保證每個代號唯一存在，且存在於依同份發布 shard map 所選中的檔案。明列其為發布不可豁免條件，沿用 guard 失敗零寫入契約。

### 2.4【Medium】事後更正只寫了一種事件順序，且與禁止重畫存在例外衝突

**問題：** D4/S9 只寫「先查無，index 隨後就緒」。若 index 已先就緒，之後才從 shard 判定缺碼，仍可能停在查無。比較頁也沒有相同矛盾的處置。另一方面，§5.3 禁止 index 完成後重畫主體，D4 又要求修改查無畫面，例外範圍未明。

**晚修成本：** 存在性錯誤處理會依到達順序分裂，最後須重訂事件與畫面更新規則。

**規格修法：** 將「同版本 index 有碼、對應有效 shard 無碼」定義為與到達順序無關的資料錯誤；涵蓋重新進頁與比較頁。明列查無更正是禁止重畫規則的有限例外，且不得影響目前其他品項。

## 3. 驗證策略缺口

以下逐條回答 S1–S17；每條都存在可假通過的弱化版本。

### 3.1【Medium】S1：互動終點仍可提前，失敗樣本還能消失

**問題／弱化反例：** 只更新排序按鈕的 `aria-pressed`、表格完全不排序，仍能通過。強制 layout＋同步派送 click 也不證明畫面已繪出、一般使用者能操作。互動失敗的樣本被「不算」，可能只留下最快的成功樣本。

**晚修成本：** 所有效能改善都會建立在錯誤終點上，須重跑整批基準與 candidate。

**堵法：** 終點要求主體可見、按鈕可操作，點擊後表格順序符合預期，且完成互動後的畫面更新。未達終點必須判該次失敗並影響整輪是否有效，不得從 median 母體直接移除。

### 3.2【Medium】S2：可搜尋尚未定義為搜尋功能真的完成

**問題／弱化反例：** 提早啟用搜尋框或提早打 `search-ready`，結果仍未產生，也能得到漂亮時間。詳情指標的 V 也不能直接代表首頁搜尋的變異。

**晚修成本：** G3 回歸可能直到使用者操作才被發現。

**堵法：** 新舊共用固定查詢與預期結果，以可操作的正確搜尋結果作終點；首頁搜尋另量自身變異。明確處理小幅超界但仍在量測不確定範圍內的結果。

### 3.3【Medium】S3：單一耗時數字掩蓋搜尋可用性的差異

**問題／弱化反例：** 只記最小片、只量搜尋框啟用，或詳情仍在畫面時讀取提早的 mark，都能交出劣化小於 1,500 ms 的文件。

**晚修成本：** 已完成快速詳情後才發現搜尋延遲驗收沒有共同基準，須重新量測。

**堵法：** 指定與 S1 相同三碼、條件及配對輪次，終點沿用 S2 的真實搜尋完成定義；明定 1,500 ms 是逐碼判定，並交代測試搜尋是否會觸發 D2 提前啟動，避免改變被量測路徑。

### 3.4【Medium】S4：只扣住一秒，驗不到 meta 等待與回應 body 階段

**問題／弱化反例：** 固定延遲 1,100 ms 後就抓 index，或 shard headers 到達就啟動 index，都可能通過。meta 很慢但 shard 只扣一秒時，測試還可能不慎跨越合法的 3,000 ms 提前條件。

**晚修成本：** 請求順序通過但真實傳輸仍互搶，效能不兌現。

**堵法：** 分別控制 meta、shard headers、body 完成與驗證完成；使用明確時間軸，斷言啟動事件只能由落定、搜尋需求或到期三者之一引起。補上失敗與快取命中的落定路徑。

### 3.5【Medium】S5：「每列一支」不等於矩陣窮舉

**問題／弱化反例：** 一支測試只替「任意」選 ready，即可完全漏掉 meta loading＋index ready、meta error＋index pending 等狀態；畫面初始狀態正確，但轉移後卡住，也會通過。

**晚修成本：** 驗收文件看似完整，實際仍須重寫轉移測試。

**堵法：** 將「任意」展開為可達組合，明列不可達組合及理由；另驗證 `popstate`、重試及資源抵達順序的轉移。除文案外，斷言可操作性、禁止請求與不得殘留前一品項。

### 3.6【Medium】S6：兩邊相同，不代表任一邊正確

**問題／弱化反例：** pending 與 ready 都顯示相同錯價、空殼或錯誤頁，`innerHTML` 仍相同。`document.title` 又不在 `#detail` 裡，D5 可完全壞掉。

**晚修成本：** 「與 index 無關」被誤當成臨床內容正確的證明。

**堵法：** 比對前先確認指定品項與完整詳情存在，並以獨立預期值核對價、狀態、生效日、紀錄及描述選擇。另斷言 title 的日期選擇與退回值。固定 status 狀態，避免非 index 差異干擾比較。

### 3.7【Medium】S7：根節點 expando 擋不住重畫子內容

**問題／弱化反例：** 保留 `#detail`，把它的 `innerHTML` 重設為相同內容；expando 還在、shard 命中快取所以請求仍為 1，三項斷言全部通過。

**晚修成本：** 不撤詳情的產品決策可能被實作成重畫，直到操作狀態遺失才發現。

**堵法：** 保存主體內關鍵子節點身分及既有互動狀態，確認 index 落定期間主體沒有替換或內容變動。先固定 status，避免其合法重畫混入；橫幅另驗證可見性與按鈕行為。

### 3.8【Medium】S8：只指名一種結構錯誤，未覆蓋 D4 全表

**問題／弱化反例：** 只特判 `records` 非陣列，其餘壞結構仍回查無。缺 `invalidRecords`、entry 為 null、描述結構不合法、shard 外層損壞、invalid JSON 均未被點名。

**晚修成本：** reason 拆分表面完成，實際仍有資料錯誤被吞成查無。

**堵法：** 對每個既有結構合法性條件設反例，並涵蓋缺 key 與 own key 存在但值壞的差別；補空碼、合法非 10 碼、network、body timeout 及 meta 不合法，逐項斷言錯誤類型與請求數。

### 3.9【Medium】S9：更正可能套到已離開的品項

**問題／弱化反例：** A 查無後轉 B，index 回來時仍把目前頁改成 A 的缺碼錯誤；原測試只停在 A，因此通過。

**晚修成本：** 錯誤訊息與目前代號脫鉤，須修改更正責任與導覽判斷。

**堵法：** 測 index 先到／後到、查無後離頁／返回、retry-shard 成功後 index 才到，以及 mismatch index 不得作更正證據；斷言只更正目前仍成立的同版本矛盾。比較頁須核對每個代號狀態。

### 3.10【Medium】S10：沒有禁止「太早」，也沒有測指定的全部觸發入口

**問題／弱化反例：** 2,000 ms 就發 index，到 3,000 ms 計數仍為 1，因此通過。只支援回搜尋按鈕，漏掉 `popstate` 與 focus，也能通過。

**晚修成本：** 防卡住機制可能持續破壞正常 fast path。

**堵法：** 在截止前斷言 0、截止後斷言 1；分測所有指定觸發入口。加入落定／計時／導覽同時交會與重試後舊計時器抵達的反例。

### 3.11【Medium】S11：重抓隔離不等於重試正確

**問題／弱化反例：** index 請求數增加，但結果永遠丟棄；或未比版本就開放搜尋。重設詳情子內容也能保留根節點。

**晚修成本：** 重試按鈕看似有作用，實際不能恢復或恢復成未驗資料。

**堵法：** 除隔離計數外，驗證成功後搜尋正確恢復、失敗仍可再試、mismatch 不開放搜尋；重試期間導覽不得被回拉，主體子節點與互動狀態須保留。

### 3.12【Medium】S12：disabled 不是未驗資料沒有外洩

**問題／弱化反例：** 搜尋框 disabled，但已渲染未驗搜尋結果，或既有事件仍可執行搜尋，仍通過。

**晚修成本：** 表面閘門正確，資料來源契約卻已被破壞。

**堵法：** 同時斷言無未驗結果、無可進入的結果連結、操作不能產生結果；meta 重試後須依目前版本正確恢復或 mismatch，不能永久停用。

### 3.13【Medium】S13：「正常顯示」沒有指定正確性與保留性質

**問題／弱化反例：** 只畫空圖表、空表格與清單容器；chip 顯示任意非空文字，就能通過模糊驗收。index 就緒時重畫比較主體也未被禁止性斷言抓到。

**晚修成本：** G2 名義完成，實際資料錯誤或互動狀態被重設。

**堵法：** 核對選定代號、序列、表格內容、預告數量與品名來源；加入主要資源錯誤／版本不符。index 落定前後保留比較／預告主體及使用者設定，只允許規格列出的外圍更新。

### 3.14【Medium】S14：直接測 guard，證明不了發布路徑零寫入

**問題／弱化反例：** `check_guards()` 正確失敗，但發布流程忽略結果或先改 status，仍能通過函式層測試。空目錄「沒寫出檔案」也驗不到既有檔案被覆寫或刪除。

**晚修成本：** 最重要的全有全無契約只有假證據。

**堵法：** 從正式發布入口注入異常，對預先存在的整個 `data/` 比對前後檔名與位元組，要求失敗退出。涵蓋兩方向差集、錯片、重複碼，且 `allow_anomaly` 不得豁免此 guard。

### 3.15【Medium】S15：真實資料 smoke 可完全沒有走 fast path

**問題／弱化反例：** 新增 smoke 仍等 index 全部到齊，再檢查詳情即可通過。現有 [`real-data.spec.mjs`](e2e/real-data.spec.mjs:1) 已有真實資料 `?code=` 檢查，單純「再加一支」沒有指定新增保護性質。

**晚修成本：** mock 與正式資料間的 fast path 落差只能到上線才發現。

**堵法：** 真實資料 smoke 明確扣住 index，核對指定 shard 的完整詳情及正確內容，之後才放行 index；至少一條走 GitHub Pages 專案子路徑。保留既有全套測試要求。

### 3.16【Medium】S16：字面升版不能證明新外殼可更新

**問題／弱化反例：** CACHE 字串遞增，但快取名稱引用不一致、外殼缺檔或 data 被意外接管，仍符合原條文。現有 Playwright 設定封鎖 SW，其他綠燈不會補上此證據。

**晚修成本：** 舊訪客才遇到資源更新失敗，開發測試卻一直正常。

**堵法：** 驗收實際的舊版外殼更新情境，確認載入 candidate 資源，並保持 data 不經 SW、清理僅限本專案的既有性質；不能只檢查版本號字面。

### 3.17【Medium】S17：沿用 gzip server 無法量出有意義的條件式快取行為

**問題／弱化反例：** 現有 [`measure_e7.mjs`](scripts/measure_e7.mjs:30) 伺服器固定回 200，沒有 ETag／條件式回應。暖載入記下一次 200 與位元組數即可交差，卻不能代表已驗證 HTTP cache。頁面看到的狀態也須區分是否為網路層 304。

**晚修成本：** 留下的回頭客數據不可解讀，未來無法作比較基準。

**堵法：** 指定量測來源、暖化程序、相同 browser context 與重新導覽方式；分開記錄網路回應狀態、實際傳輸量與取得內容大小。保持只記錄，不新增優化或效能門檻。

### 3.18【Medium】§7／M0：兩輪 median 接近，不足以證明變異受控

**問題：** 高變異樣本的兩輪 median 可能碰巧相近，使 V 接近 0；「門檻 ≥ 5V」因此不等於結果穩健。固定 legacy→candidate 的順序也未排除順序效應。現有伺服器首次請求才同步 gzip，若兩側預熱不同，會再引入非前端差異。

**晚修成本：** 會重演前案：當天過門檻，換輪次就停工；完成實作後才知道 M0 的保證不足。

**規格修法：** M0 凍結多個交錯區塊、平衡先後順序，使用能反映同版假改善分布的變異判準，不能只取一次 median 差。兩側伺服器 gzip 準備條件一致，但瀏覽器仍維持冷 cache。正式比較同時報配對改善的分布；不確定範圍跨越 2,000 ms 時應判證據不足，不調門檻，依預先凍結的補測／停工規則處置。

## 4. 更簡單的替代方案

### 4.1【Low】不必把選擇性快取失效也變成第一期的必要複雜度

**問題：** §5.3 要求 meta 重載後依全域版本或個別 shardVersion 選擇性失效，但目標只要求首訪快、index 到達不清快取；並未要求 meta 重試換批時最大化快取重用。這額外增加舊請求、共用快取與版本切換的組合。

**晚修成本：** 實作者可能先完成細粒度失效，再發現主要風險其實是世代一致性，須重整整套轉移。

**規格修法：** 可採較簡單的行為契約：一次顯示使用固定 meta 世代；index 完成不影響 shard 快取；meta 重試若仍同版便保留，若換版則整體重新建立該世代的衍生視圖與快取。犧牲只限錯誤恢復時的額外重抓，不影響 G1、G3，也不引入持久快取、框架或 build step。D1 的兩種資源狀態本身合理，無須另增通用載入框架。

**總計：Blocker 0 項／High 5 項／Medium 23 項／Low 1 項。**
