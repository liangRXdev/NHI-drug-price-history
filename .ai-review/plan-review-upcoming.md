## 1. 需求與邊界缺漏

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | **§4 事件表不完整，且混淆事件與支付狀態。** `initial` 未定義；`unchanged` 也可能是終止→終止、暫停→暫停，不能一律叫「續期（價格未變）」。首列 0 元的事件通常是 `initial`，連續 0 元可能是 `unchanged`，都不受目前 `eventType=terminated` 的例外保護。 | UI、篩選、CSV 若都以目前事件表建模，之後須共同修改分類契約；只補一個標籤無法解決。 | 定義涵蓋 `eventType × priceState × everPriced` 的呈現決策表。首列 0 元例外以支付狀態及此前有價史判定，不限事件名稱；保留 record 原事件，不重算。停止狀態續期不得說成有價續期。 |
| **Medium** | **§4／§5.2 未完整實現「從多少變多少、幅度多少」。** `relisted` 只顯示新價，雖資料已提供停止前價格、差額與百分比；暫停前價格可能為 null。暫停原始標記固定寫 `-`，未涵蓋 `－`、`—`。 | 卡片與 CSV 容易各自補規則，造成同一事件不同答案。 | 明定每類事件的前價、後價、差額與百分比適用性；恢復支付呈現既有比較值並標註跨越停止期間；null 不得轉 0。暫停展示實際 `rawPrice`。 |
| **Medium** | **§5.1 徽章有三種不相容的數量語意。** `count` 是 `from>D` 的列數，不能同時代表 `effectiveDate>T`；§3.4 只新增 meta 欄位，未定義 status 如何產生 `upcomingRows`。 | ETL、入口與清單各自使用不同數字，跨日後必然失配。 | 分清「檔案總列數」「T 之後列數」「不同代號數」。最簡相容方案是未載入前只顯示「預告」，載入後才顯示依 T 計算的數量。批次標題也明定計列或計代號。 |
| **Medium** | **§2 日期與過期提示不完整。** 新鮮的 `lastCheckedAt` 可與很舊的 `buildDate` 並存，套用 §8.6 不一定產生警示；全部過期時的訊息是否取代清單也不清楚。`T<D` 時則可能有仍屬未來、但已被 build 排除的紀錄。 | 日期邏輯會散落在徽章、卡片、空態與匯出，之後難以保持一致。 | 明定到期提示獨立於最後檢查日警示，且不取代保留列；標示 D 與本次參考 T。沿用不跨午夜自動更新的取捨，明定進入頁面時更新 T。`T<D` 時提示快照涵蓋限制，不宣稱清單完整。 |
| **Medium** | **§5.3 篩選／排序契約不閉合。** `date` 沒有篩選語意；排序未定義 URL 參數；「其他」未列事件集合；「幅度 desc」不知是帶正負數值或絕對幅度，也未說明與日期分組的優先關係。 | 各控制項可以各自「正常」，但分享 URL 或組合操作產生不同結果。 | 列出各參數的合法值、預設、無效值處理及組合關係；明定日期為精確批次或其他既定語意、幅度比較方式、分組優先與同值順序。空篩選訊息中的 N 指明為篩選前總列數。 |
| **Medium** | **§5.5 只寫「缺欄位」，沒有合法內容的判準。** 合法 JSON 仍可能含錯誤日期、型別、計數或其中一筆壞列；逾時、meta 失敗與成功後再失敗的處理未明列。§7 又要求 404 隱藏徽章，與 §5.5 的「—」衝突。 | 容易先做成跳過壞列的寬鬆解析，後續必須重整錯誤與重試流程。 | 明定整份資料的必要欄位、合法 null、日期與計數一致性；任一列不合法不得部分呈現。非成功 HTTP、逾時、meta 不可用皆有有限等待及可恢復錯誤狀態；統一 404 徽章規則。 |
| **Medium** | **§5.4 CSV「文字欄位」不是 CSV 本身提供的型別。** BOM 與引號不能保證 Excel 保留 `0.00`；來源前言、欄名列與資料列的計數也未區分，備註未規定是否攜帶到期與品質提示。 | 匯出檔一旦被用於對帳，修正欄位語意會影響既有使用方式。 | 保留 CSV 範圍，指定受支援的 Excel 開啟／匯入流程及精確字串驗收；明定前言、標頭、資料列結構，並讓 CSV 保留畫面必要的到期、異常與跨停止期間語意。 |

## 2. 架構風險

|---|---|---|---|
| **Blocker** | **§3.4 與 U6 要求預告產生失敗仍發布其他資料。** 這引入部分發布，與題述 (a)7 的全有全無契約，以及上位 §12／§14 的驗證後發布方向衝突。舊 upcoming 可能留下，新 meta 計數如何處理也未定義。 | 發布流程與測試會朝相反方向建立；之後須重做錯誤邊界。 | 本次以既定全有全無契約為準：預告生成或驗證失敗，整批不發布，既有 data/status 不變；改寫 U6。若希望將它變為可獨立失敗的產品，屬另外修改發布契約，不能在此默默引入。 |
| **Blocker** | **§7 的 network-first／離線快取直接違反 (a)2。** 現有 `sw.js` 明確讓全部 `data/` 不經 SW。 | 實作後會建立另一套資料新鮮度與錯誤路徑，移除時需連帶修改離線 UI 與驗收。 | 刪除預告資料 SW 快取要求；沿用 data 走網路，離線呈現不可用與重試。不得以離線標籤作為推翻既定限制的理由。 |
| **High** | **§3.3 的「來源無變不動 upcoming」「與 index 同進退」與上位 B5 不相容。** B5 明定同 CSV 跨預告生效日會更新 index；題述 (a)6 則要求來源無變只更新 status。另外「最舊落後一個 build 週期」沒有上限保證。 | 資料批次、diff 判定與日期測試會各自形成不同定義，後補會改動發布契約。 | 依本次明確限制，採來源無變只更新 status；同步修訂上位 B5 的跨日例外，消除雙重規則。刪除最多落後一週的宣稱；清单產生時間可能停留至下一次來源變動，最後檢查時間另行呈現。 |
| **High** | **§3.3／U7 沒有首次上線及修復既有衍生檔的路徑。** 新功能部署時來源可能未變，因此 `upcoming.json` 永遠不產生；生成規則修正也可能被「來源無變」擋住。 | 功能完成後才發現無法交付有效資料，需臨時改發布規則。 | 明定新版本首次交付包含經驗證的初始 upcoming；規則修正屬明確版本遷移，不混入例行週檢查。遷移與例行 build 分別驗收，`dataVersion` 仍保持只依來源內容。 |
| **Medium** | **§6 詳細頁連結要求知道「是否在預告清單中」，又禁止詳細頁讀 upcoming。** 依 T 的 history 預告與依 D 的已發布清單，在跨日後不一定相同。 | 容易為一個連結新增隱藏資料依賴，破壞詳細頁單一真相。 | 取消精確成員判斷，改為一般「前往預告中心」連結；或明定以 history 與已發布 D 判定，且 D 必須有既定可靠來源。不得改讀 index 摘要或 upcoming 取得詳細頁資訊。 |
| **Medium** | **§8 將 lazy fetch 等同首屏 0 bytes，量測範圍不成立。** 新增 HTML／JS／CSS 仍可能增加外殼成本；原生 module 不會自動排除未使用功能。fetch→渲染也未定義是否包括 meta、字型及實際繪製。 | 可能為字面 0 bytes 被迫重構載入架構，或以漏算成本的測試宣告通過。 | 將 0 bytes 精確限定為「未進入預告頁前，新增預告資料傳輸為 0」；另記錄外殼增量。定義效能起訖、冷暖快取與必要依賴，不重開已接受的 E7 優化工作。 |

- **U4：沒有實例。** 62 筆未來 terminated 全都有此前有價紀錄。完整清單人工目檢也無法驗證這個例外。

- 全量未來事件也沒有 initial、suspended、relisted、first_priced、unknown；必須用指名反例補足，不能以「掃完 82 列」替代。
- U8 若只使用目前日期與現況資料，尚未觸發到期分支；U6、U10、U11 的失敗／混批條件都必須主動注入。

## 4. 更簡單的替代方案

| 嚴重度 | 問題 | 為什麼現在不修之後會更貴 | 建議修法 |
|---|---|---|---|
| **High** | 為小型衍生清單引入獨立失敗發布、SW 快取及離線狀態，複雜度主要來自一致性管理。 | 每多一個發布／快取狀態，就增加混批與恢復組合。 | 保留「完整 history 產生單一 upcoming 檔、進頁才載入、同批驗證發布、data 不經 SW」。符合純靜態與無 build step 的前端限制。 |
| **Medium** | 精確首屏徽章需要 status 新欄位，卻仍無法從單一數字算出跨日剩餘數量。 | 為非核心入口數字建立額外資料契約。 | 首屏只顯示「預告」，進頁後才計數；移除 status 計數擴充，meta 的統計可繼續供建置紀錄。 |
| **Medium** | 詳細頁的精確清單成員連結帶來不必要依賴。 | 日期不同步時還要解決「連結在／不在」的一致性。 | 使用一般預告中心入口，不宣稱該品項一定在當前清單；詳細頁預告仍完全由 history 判定。 |

以上建議均為修正現有目標的契約或刪減元件，未加入訂閱、政策推論、採購建議、後端或其他非目標功能。
