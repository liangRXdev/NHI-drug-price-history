### F1 — High：停止續期需要的前價，輸出模型仍然沒有

- **問題：** §4.1 要求「終止支付續期／暫停支付續期」顯示停止前 X 元；§4.2 要求取此前最後一個 `priced`，但 §3.1 又限定 `previousPrice` 直接取 record，不重算。

  上位 `spec.md` §5.4 明定：
  - `terminated → terminated`：`previousPrice = null`
  - `suspended → suspended`：`previousPrice = null`

  `everPriced=true` 只能證明曾有價，無法還原金額。上位 §5.1 已因同一問題替 index window 增加 `pricedBefore`，並記錄實測有 45 個代號受影響；upcoming 未提供等價資料。

  因此按 §3.1 正確產生的資料，仍無法滿足 §4.1。套用「null 就省略」只是掩蓋缺資料，沒有完成已接受的前價需求。
- **為什麼晚修更貴：** 須同步修改衍生檔模型、合法性、卡片及 CSV；不是補文案即可解決。
- **建議修法：** 在 upcoming 契約中明確攜帶「該列之前最後一個有價金額」，與事件的 `previousPrice` 分開定義；由完整 history 產生，保留 record 原事件欄位不變。這是補足既有前價需求，不需要讓前端另載 history。

### F2 — High：新呈現表不窮盡、不互斥，篩選又混用兩種分類

- **問題：**
  1. 合法序列 `[10, missing, 12]` 的最後一筆是 `priced`、`everPriced=true`、`previousState=missing`，**沒有任何一列可套用**。`malformed` 同理。這也是上位 `plan.md` A3 已指定的反例。
  2. 帶 `conflicting_price_interval` 的 `priced` 列，同時符合一般價格列及末列「無法判定」，**沒有指定優先序**。
  3. 上位 `eventType=unknown` 還涵蓋不同價格／狀態的 overlap，不限同起迄日衝突。新表只以 `conflicting_price_interval` 兜底，可能把不可判定事件重新標成確定調升／調降。
  4. §5.3 的 `type` 看似使用原始 `eventType`，但 `other` 又包含 `missing`、`malformed`、「無法判定」——這些並非同一組原始事件值。`initial`、各種 `unchanged`、首列 0 元到底落在哪個選項，仍無完整映射。

  例如首列 0 元標籤已修成「健保支付價 0 元」，卻可能因 `priceState=terminated` 被歸入「終止」篩選；或因 `eventType=initial` 而在所有具名類別中消失。
- **為什麼晚修更貴：** 分類會同時進入資料解讀、URL、卡片及 CSV，事後修正須共同調整。
- **建議修法：** 保留原始事件不變，另將呈現及篩選映射完整列出；明定異常／不可判定的優先序，補齊前筆 missing／malformed、不同區間 overlap，以及 initial／unchanged 的歸類。首列 0 元例外須跨標籤、篩選及 CSV 一致。

### F3 — Medium：四層合法性尚未形成可執行的完整契約

- **問題：**
  - U3 要求「只有未來列時描述為缺值」，§5.5.1 卻只允許六個欄位為 null，「其餘不可」。上位只規定畫面顯示「—」，沒有替 upcoming 定義缺值究竟是空字串、null 或省略。不能據此斷言所有合法缺值都能被接受。
  - 列層僅要求部分欄位「存在」，未完整限定型別及列舉值。例如 `everPriced="false"`、未知 `eventType`、非陣列 `flags` 的處置未明。
  - `price` 可為 null 或正數，卻沒有與 `priceState` 綁定；`priced + null`、`terminated + 正數` 都能符合字面條件。
  - 未明定有效日期與 `buildDate`、`endDate` 的關係；語法合法不等於符合本檔的預告集合契約。
- **為什麼晚修更貴：** 生成器與前端可能各自採不同缺值及合法性定義。B1 又會放大錯誤驗證的影響，使合法來源阻斷整批發布。
- **建議修法：** 為 §3.1 全部欄位指定必要性、型別及缺值表示；列出沿用上位模型的狀態／價格一致性與日期關係。驗收同時涵蓋「合法缺值接受」及「非法組合拒絕」。

**特別回答 `count` 問題：** `count = items.length`、`codeCount = 相異 code 數` 本身正確，**無新問題**。必須檢查的是原始完整 `items`，不能拿經 T、篩選或去重後的集合比較；同代號同日多列也不能先合併。

### F4 — High：首次／遷移只有「重產」，沒有完整的發布完成定義

- **問題：** §3.3.1 沒有定義：
  - 哪個可重現條件判定這次是首次或遷移；
  - 判定對象是已發布版本，還是工作目錄；
  - 已存在舊 `upcoming.json` 時如何確認仍須遷移；
  - 失敗後重跑是否仍屬未完成遷移；
  - index/history 無差異時，如何確認新檔與 meta 已實際進入發布。

  交叉驗證的 workflow 確實只以 index/history 判定 changed；無差異分支僅提交 status。**產出檔案不等於發布檔案**。U7b 目前只驗「缺檔仍產出」，無法堵住這個缺口。
- **為什麼晚修更貴：** 功能及資料均可能已完成，卻在部署時被例行分支排除；之後須補發布模式及遷移狀態。
- **建議修法：** 規格明定例行／遷移的可重現輸入、判定責任及完成條件；首次與遷移都必須以「經驗證的產物及相應 meta 已同批發布」完成，不能以檔案存在完成。失敗不得推進完成狀態。U7b 分別驗缺檔首次、已有舊檔遷移及失敗重跑。

### F5 — High：同來源的規則遷移，無法由 `dataVersion` 辨識

- **問題：** §3.3.1 明確允許生成規則修正而 `dataVersion` 不變。此時舊 upcoming 與新 meta 仍可版本相等，且都通過結構驗證；U11 完全偵測不到「舊規則產物被當成已遷移資料」。

  B1 保證發布前的整批驗證，不保證瀏覽器跨請求取得同一次部署。B2 移除 SW 也不會移除 HTTP／CDN 快取；上位 D10 已明確記錄這類混批風險。
- **為什麼晚修更貴：** 之後才加辨識契約，須同步改產物、meta、相容性及載入驗收。
- **建議修法：** **[新增需求：衍生產物修訂辨識]** 增加獨立於來源 `dataVersion` 的 upcoming 產物辨識契約，用來確認規則遷移後應取得的產物。否則必須明確承認 U11 只能驗來源一致，不能驗遷移完成或衍生檔新鮮度。此建議不改 `dataVersion`，不改 history shard，也不引入 SW。

### F6 — Medium：成功後更新失敗的規則，與 U10 直接相反

- **問題：** §5.5 要求「保留現有清單＋更新失敗橫幅」；U10 卻要求六種失敗「均不得呈現清單」，並把「成功後再失敗殘留舊列」列為應殺掉的弱化實作。

  相同操作序列無法同時滿足兩者。若失敗為新版資料損毀或版本不一致，保留舊清單規則與「不渲染、不匯出」的優先關係也未定義。
- **為什麼晚修更貴：** 會先建立互相對立的狀態流程與測試，整合時才發現無法全綠。
- **建議修法：** 分開規定「首次載入失敗」與「已有成功快照後更新失敗」，再明定網路失敗、內容非法及版本不一致各自的顯示／匯出結果。若保留清單，必須連同原本驗證過的版本、D 及提示保留，不能配上新的成功狀態。

### F7 — Medium：U14 把目標升格為驗收，卻未完成量測及失敗契約

- **問題：**
  - 「fetch → 首次可捲動，不含 meta」未說 meta 是預先完成，還是事後扣除等待；但 §5.5 又禁止未驗版本就呈現清單。
  - 未固定樣本、重複次數及統計量；單次結果與中位數可能導致相反判定。
  - gzip 從 100 KB 收緊至 20 KB，理由只有目前約 6 KB。合法公告量增加時，是驗收失敗、僅記錄，還是影響資料發布，沒有說清楚。
- **為什麼晚修更貴：** 功能完成後容易為通過測試改量測起點，或臨時放寬門檻；也可能把合法資料成長誤判為必須刪減資料。
- **建議修法：** 固定資料集、網路數值、meta 前置狀態、起訖及統計方式，區分功能驗收與例行資料 guard 的後果。不得以省列、提前顯示未驗證結果通過效能。

**不應宣稱 200 ms 數學上必然不可達。** 既有驗收記錄使用約 60 ms 網路延遲，單憑「Fast 4G」不能推出這個結論；真正明確不可同時滿足的是 F6。

### F8 — Low：H2 修正後，日期說明仍保留舊結論

- **問題：** §2、§11.5 仍說來源長期未變時，D 停在「上游最後一次變動的那次 build」。依新 §3.3，跨生效日也可重建，首次及遷移更不依來源變動。

  此外，題述 (a)6「上游無變動時只更新 status」若按絕對規則閱讀，仍與保留 B5 的處置衝突。
- **為什麼晚修更貴：** 發布行為可能正確，但文件、驗收及使用者對日期的解釋會相反。
- **建議修法：** 將 D 說明改為「目前已發布 upcoming 的產生日」；將 status-only 明確限定於無資料差異、無日期衍生差異、也無首次／遷移的例行情況。**不需修改 B5 的跨日行為。**

## 2. 新架構是否成立

**成立，但目前只有發布前的失敗方向成立，端到端契約尚未閉合。**

| 架構部分 | 判定 |
|---|---|
| 完整 history 產生單一 upcoming | 成立；可保留多筆預告及原始事件 |
| 任一生成／驗證失敗整批不發布 | 成立；與既有全有全無契約相容 |
| upcoming 不經 SW | 成立；不必加回離線 fallback |
| 進入預告頁才載入資料 | 成立；不需要重開已接受的 E7 優化 |
| 例行與首次／遷移發布 | F4 未解前不完整 |
| `dataVersion` 作來源一致性驗證 | 成立 |
| `dataVersion` 同時證明遷移產物正確 | 不成立，見 F5 |

B1 的必要後果是：upcoming 驗證錯誤會阻斷搜尋資料與 status 更新。這是既定取捨，**不是應恢復部分發布的理由**；因此 F3 的合法資料接受範圍尤其重要。

B2 也不支持「版本不一致永久無法恢復」的絕對說法。重試取得一致資料可以恢復；真正需要驗收的是恢復結果，以及同來源遷移無法靠來源 hash 發現的缺口。

**兩條部分接受的最終判定：**

- **H2：接受覆核者保留 B5 的方向。** workflow 證據支持它；尚須補 F4、F8，不能把「本地重產」當成「已同批發布」。
- **M6：接受。** CSV 的可交付契約以原字串、跳脫、BOM 及完整欄列為準合理。README 說明 Excel 匯入限制足夠，無需新增特定 Office 版本的相容性驗收。

| **U10** | 目前與 §5.5 相反，不能作為單一正確驗收 | **Medium**：會逼迫刪掉其中一方測試。依 F6 分開首次失敗與成功後失敗 |
| **U11** | 舊規則 upcoming 與新 meta 使用相同 `dataVersion`，仍可當成一致資料呈現 | **High**：晚修須改辨識契約。增加同來源、不同產物修訂案例，見 F5 |
| **U12** | 若只把 CSV 對應到已算錯的篩選結果／畫面標籤，錯誤可被完整複製到匯出 | **Medium**：晚修涉及對帳欄位。指定獨立預期的事件、前後價、差額、到期及品質備註；原字串與跳脫部分**無新問題** |
| **U13** | 把所有列都加品質 chip 仍符合「非空者必有」；手機只顯示免責全文但卡片被截斷也能通過 | **Medium**：晚修需調整整合畫面。加入無旗標負對照及 §5.2 必要欄位可見性；計數僅適用有分組的排序模式 |
| **U14** | 以空清單／少量資料量測，或提前讓骨架可捲動，仍可能報符合門檻 | **Medium**：晚修才暴露真實效能。固定完整預期列集合與成功驗證後的可捲動終點，見 F7 |

合成資料方面，U4 的 `terminated` 事件且此前無 priced **可以成立**，例如暫停後轉 0 元；不能因真實預告母體沒有這類列就判定 fixture 不合法。反之，U2 若使用完全相同來源列，會被上位去重規則消除，必須保證是應保留的不同紀錄。

## 4. 仍然過度或仍然不足之處

**可直接保留、不必再加複雜度的修訂：**

- 徽章未載入前不帶數字。
- meta 統計僅供建置紀錄及 warning；它不是必要的前端依賴，但保留合理。
- `change_desc` 取消分組；§5.3 已明確給出對 §5.2 預設版面的例外，**沒有實質衝突**。
- CSV 位元組契約與 Excel 已知限制分離。
- 詳細頁保留 history 單一真相及一般入口。
- 全有全無發布與 data 不經 SW。

**仍然不足、應在下一版定案的範圍：**

1. 前價資料與完整分類／篩選映射。
2. 欄位缺值、型別及狀態一致性的合法性契約。
3. 首次／遷移的可重現判定、發布完成及產物辨識。
4. 首次失敗與成功後更新失敗的狀態優先序。
5. 將上述分支綁到精確驗收，並固定 U14 的量測契約。

本輪沒有需要推翻 B1、B2 的新 Blocker；需要修的是它們與資料模型、遷移及驗收之間尚未接合的契約。
