## A. 第一輪項目的修訂是否到位

### A1 — Medium｜第一輪 3.1：排序終點與最小片樣本不相容

- **問題：** §7 強制選最小 gzip 分片，又要求點擊排序後首列日期「變為預期的另一端日期」。實際最小片為 `NB01.json`，gzip level 6 為 **637 B**；只有 `NB01043100`，且只有一筆紀錄，日期為 `2012-03-01`。正確實作也無法讓日期改變，M0 會不斷作廢重跑。
- **為什麼現在不修之後會更貴：** 量測腳本完成後才會發現必選樣本永遠無法通過，屆時容易臨時換碼或放寬終點，破壞實作前凍結。
- **建議修法（規格層）：** 保留最小片樣本，明定單筆紀錄的互動終點；多日期樣本仍須驗證實際排序結果。兩種終點皆由新舊共用觀察規則判定，不得事後換碼。

### A2 — Medium｜第一輪 3.5：S5 仍容許每列只挑一種組合

- **問題：** S5 仍寫「M1–M13 各一支 e2e」，但 M8、M10、M11、M13 各含多種組合。弱化實作可以只測 M10 的 index ready，漏掉 index error／mismatch 時詳情的正確內容與橫幅；S5b 也未補滿這些組合。「已堵一支測試只替任意挑一值」與實際條文不符。
- **為什麼現在不修之後會更貴：** 驗收文件可以十三列全勾，之後仍須重新盤點與補寫組合測試。
- **建議修法（規格層）：** 明定驗收單位是展開後的可達組合，並列出各組合的必要斷言；一支測試可以涵蓋多組合，但須分別有證據。

### A3 — Medium｜第一輪 2.4：比較頁的「有限例外」範圍仍不一致

- **問題：** D4.3 的定義限於「驗版成功的 shard 缺 own key」，但比較頁條款卻寫成任何 `missing` 且 index 含碼就改為 error。現有比較流程在**無匹配前綴**時也產生 `missing`（`app.js:1136`）。因此比較頁可更正這種情況，詳情頁第 4 列卻不在例外內。
- **為什麼現在不修之後會更貴：** 相同資料矛盾在兩個視圖會得到不同分類；若只保存籠統的 `missing`，之後還須補足判定依據。
- **建議修法（規格層）：** 明定比較頁例外也必須具有「對應 shard 已驗版且缺 own key」的證據；若要涵蓋無匹配前綴，須同步明列詳情頁的規則，不能由「比較頁同規則」暗中擴張。

### A4 — Medium｜第一輪 3.8：S8 仍未逐一覆蓋結構合法性條件

- **問題：** 可具體寫出只拒絕已列反例的弱化版本：仍接受非物件 shard、非字串 `shardVersion`、重複或空字串的 `files` 成員、空字串 version。這些都違反 D4.1／§5.7，但 S8 指名清單未要求逐項反例；「十列逐列測」也不等於測完每列內的所有條件。
- **為什麼現在不修之後會更貴：** reason 拆分與 meta 強化可以名義完成，資料缺陷仍進入正常或查無路徑。
- **建議修法（規格層）：** 將每個結構條件及 §5.7 每個限制逐一對應反例與預期分類，明定不得只為一列選一個代表案例。

### A5 — Medium｜第一輪 3.9：S9 遺漏返回與重試後的更正資格

- **問題：** 原要求的「離頁後返回」與「`retry-shard` 成功後 index 才發布」未寫入 S9。弱化實作可保留第一次缺碼的更正資格：重試已取得完整詳情，index 到達後仍把它改成缺碼錯誤。現有 S9 六支均可通過。
- **為什麼現在不修之後會更貴：** 這會直到使用者重試或返回時才出現，必須重新釐清目前畫面與歷史請求的關係。
- **建議修法（規格層）：** 補回兩條操作序列，斷言更正只依目前仍成立的第 8 列狀態；成功詳情不得被先前缺碼結果覆蓋。

### A6 — Medium｜第一輪 3.3：S3 的量測終點仍有兩種解讀

- **問題：** §7 以真實查詢結果收秒表，S3 卻要求先等詳情可互動，再等待 mark、切搜尋、查詢。legacy 的搜尋可能早在 shard 完成前就可用；若以最後查詢結果計時，legacy 被額外加上等待詳情的時間，會低估 candidate 的搜尋劣化。若改讀 mark 時間，又與 §7 終點不同。
- **為什麼現在不修之後會更貴：** 相同資料可產出不同的 1,500 ms 判定，量測完成後仍須重跑。
- **建議修法（規格層）：** 明確指定 S3 收秒表的事件，以及 legacy 的搜尋已先可用時如何計時；後續真實查詢驗證不得把等待詳情的時間回灌為 legacy 的搜尋可用時間。

對五項「部分接受」的判定：

- **1.3：理由成立。** 有限逾時加 T1／T2，可取代計時器，不必恢復。
- **1.6：理由成立。** 強化既有 meta 合法性不動架構或資料模型，列 Medium 合理。
- **3.10：理由成立。** 刪除計時器與不可達的 focus 入口合理；其他入口仍須實際驗證。
- **3.16：理由成立。** 可由人工舊版裝置更新驗收承擔本案證據，不必新增 SW e2e 基礎設施；但 network-first 本身不能代替該驗收。
- **3.18：理由成立。** 本案可採預先凍結的經驗性區塊判準，無須強加信賴區間；不能把有限樣本最大值宣稱為未來變異的保證。

## B. v0.2 新引入的問題

### B1 — Medium｜補入比較主體的品名 fallback，與主體零 mutation 衝突

- **問題：** I2、§5.2、§5.3 要求 index 發布後補上比較主體的品名 fallback；S13 同時要求比較主體零 mutation。現有 fallback 位於 `#compareBody` 內（`app.js:1205` 附近）。當 `selectMeta` 回 null 時，從空字串補成 index 品名必然產生 mutation。D4.3 又自稱主體更新的唯一例外。
- **為什麼現在不修之後會更貴：** 實作者必須在「不補品名」與「違反零 mutation」之間自行選邊，測試與產品契約會分裂。
- **建議修法（規格層）：** 明列品名 fallback 更新的精確範圍，與 D4.3 並列為允許的局部變動；S13 對其餘主體維持零 mutation，並驗證 fallback 品名正確。不得因此放寬為整個主體可重畫。

### B2 — Medium｜D4.1 與 M10 沒有交代等待 shard 的顯示狀態

- **問題：** `meta` ready、前綴存在、shard 尚在途，是必經狀態；D4.1 十列卻沒有這一列。依其「第一個成立者決定顯示」的字面，尚未取得 shard 也可能被當成外層不合法。M10 又把顯示限定為第 4–10 列，並遺漏 ready 時仍可成立的第 1 列。
- **為什麼現在不修之後會更貴：** 詳情閘門、錯誤分類與狀態測試會採不同解讀，容易短暫顯示錯誤或提前判定查無。
- **建議修法（規格層）：** 明列 shard loading；限定第 5–10 列於請求落定後評估；修正 M10，涵蓋語法無效與 shard loading。

其餘新契約查核結果：

- **I1／I2 可自洽。** 現有預告中心只重抓 `upcoming.json`，沒有另一條 meta 重抓流程；`retry-core` 則已由 §5.4 明確改約。
- **T1／T2 未發現必然讓 index 永不啟動的合法路徑。** 零請求、失敗及離頁均已有出口。
- **§5.6 可由 Python 獨立實作。** 最長前綴選片及唯一歸屬的文字定義足夠，不需要依賴前端程式。
- **§7.2 三種結果的分流可成立。** 未發現必須引入進階統計才能解決的矛盾；目前先須修正 A1、A6。

## C. S1–S17、S5b 的殘餘弱化版本

以下不重列 A、B 已涵蓋的漏洞。

### C1 — Medium｜S10 可放過比較／預告入口過早啟動 index

- **問題：** 弱化實作可以讓比較頁在**第一片** shard 落定就啟動 index，不等第二片；也可以在預告請求發出時立即啟動。S4 只測單品詳情，S10(a) 未指定多請求與預告情境，S13 也沒有驗證這段請求順序，因此仍可全綠。
- **為什麼現在不修之後會更貴：** G2 看似完成，但主要資源仍與 index 搶頻寬，T1 的共同契約沒有兌現。
- **建議修法（規格層）：** 分別要求比較頁一片完成、另一片 body pending 時 index 為零，以及預告 body pending 時 index 為零；全部落定後才恰一次。補單碼轉詳情的相同斷言。

### C2 — Medium｜S12 可放過 meta 尚在途時的暫時外洩

- **問題：** 弱化實作可以在首頁 index 先成功時立即發布；等 meta 最後回 500 才清空。S12 只驗失敗後的結果，仍能通過。S5 的 M1 若只把 index 固定為 pending，也抓不到這段外洩。
- **為什麼現在不修之後會更貴：** 未驗版內容可能短暫產生可點擊結果，使用者已進入後才被清掉；事後檢查最終畫面不會留下證據。
- **建議修法（規格層）：** 明列「meta body 持續扣住、index 已完整成功」的持續觀察區間；期間不得有結果、品名或可進入連結。再分別放行相符、不符與失敗的 meta。

### C3 — Medium｜S14 可放過固定四碼或非最長前綴的守門

- **問題：** 真實 shard map 全為四碼。若錯片注入只是把代號搬到無關分片，固定四碼、取第一個匹配前綴的弱化守門，也會拒絕四種注入並通過真實資料；仍未證明它遵守最長前綴契約。
- **為什麼現在不修之後會更貴：** 分片清單日後合法出現不同長度前綴時，發布守門才暴露錯誤，跨語言縱深防禦實際失效。
- **建議修法（規格層）：** 加入具有包含關係的不同長度前綴 fixture，固定正確歸屬；要求 Python 守門與 JS 選片各自符合獨立預期值。這是既有分片契約的驗證，不改資料格式。
